# Инкрементальный план миграции

| № | Этап | Содержание | Результат |
|---|---|---|---|
| 1 | Data discovery | Аудит систем FU и RB: каталогизация источников, таблиц, потоков данных, владельцев; согласование сущностей с логической моделью | Сформированный реестр систем и данных, зарегистрированный в DataHub в качестве базовой точки отсчёта |
| 2 | MDM Foundation & клиентский матчинг | Установка MDM Customer Hub, проектирование и настройка алгоритмов сопоставления данных клиентов FU и RB, первый запуск процедуры дедупликации | Формирование золотой записи клиента с глобальным client_id, перечень неразрешённых дублей для ручной обработки |
| 3 | Простой DWH и минимальные витрины (промежуточное состояние) | Инсталляция DWH на PostgreSQL, настройка batch-конвейеров из FU Core и RB Core, формирование базового набора витрин для BI-аналитики | Достижение промежуточного состояния: консолидированная управленческая отчётность по клиентам, счетам, продуктам и операциям |
| 4 | Integration Layer & Kafka/CDC rollout | Развёртывание API Gateway/ESB, брокера Kafka, Debezium-коннекторов для операционных платформ | Рабочая событийная инфраструктура, запуск первых CDC-потоков из FU Core в Kafka |
| 5 | Data Lakehouse: платформа + миграция истории | Установка Iceberg + Trino, batch-миграция архивов карточных операций и транзакций RB, конфигурирование потокового приёма новых событий | Data Lakehouse с полной историей FU и RB, доступный через SQL-интерфейс Trino |
| 6 | Консолидация Core Banking, Card, Lending платформ | Трансфер счетов, договоров, карточного и кредитного портфеля RetailBank на целевые платформы FU с унификацией статусных моделей | Объединённые платформы Core Banking, Card и Lending, обслуживающие клиентскую базу обеих организаций |
| 7 | Cutover критичных доменов | Переключение доменов Клиентские данные (детализация в cutover-plan.md) и Управленческая и регуляторная отчётность на целевые источники | Стабильные потоки на MDM/DWH/Lakehouse как единые источники истины для ключевых доменов |
| 8 | Вывод из эксплуатации RB-систем и публикация data-продуктов | Декомиссия RB CRM, RB Core, RB Cards, RB Loans, RB DWH, RB BI и точечных интеграций; регистрация 5 доменных data-продуктов в DataHub с назначенными владельцами | Финальный ландшафт из migration-target-state.md, governance-модель Data Mesh на базе единой платформы |

## Логика последовательности

- Фазы 1-3 создают **переходный ландшафт** (3 месяца) с частичной параллельностью: конвейер DWH (фаза 3) запускается одновременно с матчингом клиентов (фаза 2), поскольку начальные витрины не требуют готовой золотой записи и могут оперировать промежуточным маппингом client_id.
- Фазы 4-6 представляют собой основной цикл консолидации (месяцы 3-9): инфраструктура Integration Layer и Lakehouse разворачивается синхронно, поскольку не имеет между собой прямой зависимости; унификация Core/Card/Lending начинается лишь после готовности Integration Layer, чтобы перенос портфелей происходил через CDC, а не через разовое экспортирование данных.
- Фаза 7 (cutover) намерено выделена в самостоятельный этап **после** готовности целевых платформ: переключение критических доменов невозможно на незавершённую инфраструктуру.
- Фаза 8 (decommissioning) выполняется последней, исключительно по завершении cutover и периода параллельной валидации, чтобы обеспечить возможность отката (см. cutover-plan.md и migration-risks.md).

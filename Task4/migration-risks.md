# Риски миграции

| Риск | Влияние | Вероятность | Миграция |
|---|---|---|---|
| **Образование дубликатов клиентских профилей после объединения FU и RetailBank** | Формирование множественных записей на одного клиента → ошибки в персонализации, двукратные коммуникации, искажённые KPI и отчёты, потенциальные нарушения GDPR | Высокая | Применение многосоставных правил матчинга (ИНН/СНИЛС + ФИО + дата рождения); использование нечёткого сравнения (например, расстояние Левенштейна для ФИО); ручная верификация спорных случаев; контроль доли недвусмысленных дублей (целевой уровень > 99.8%); проведение dry-run перед каждым этапом cutover |
| **Расхождение статусов и остатков по счетам, картам и кредитам между legacy-системами и DWH** | Некорректная агрегация в отчётах, ошибки регуляторной отчётности, неверные балансы в UI, риск регуляторных санкций | Средняя-Высокая | Разработка явного маппинга статусных моделей с утверждением риск-менеджментом и финансовым департаментом; ежедневное количественное примирение (сверка counts и сумм); внедрение dbt-тестов и Great Expectations для автоматической валидации схем; фиксация допустимой дельты <= 0.01% |
| **Утрата или искажение истории операций при миграции архивов RetailBank** | Невозможность восстановления полной истории клиентов, пробелы в антифрод-анализе и риск-моделях, усложнение расследований | Средняя | Загрузка исходных выгрузок в raw-слой Data Lakehouse как есть до трансформации; сохранение неизменяемого журнала; сверка количества записей с источниками; обеспечение трассировки event_id к kafka_event_id |
| **Деградация производительности клиентских сервисов в переходный период** | Увеличение времени отклика BI-дашбордов и UI, невозможность аналитиков работать с данными, ухудшение пользовательского опыта | Средняя-Высокая | Вынос batch-выгрузок в окна минимальной нагрузки; лимиты пропускной способности CDC-коннекторов; заблаговременное создание индексов (customer_id, transaction_date, master_customer_id); настройка predicate pushdown в Trino; нагрузочное тестирование перед каждым этапом консолидации; мониторинг p99 latency в Prometheus |
| **Задержка синхронизации санкционных списков и справочника контрагентов** | Пропуск подозрительных операций, нарушение AML-требований, регуляторные санкции | Низкая-Средняя | Приоритетное подключение потока контрагентов к CDC на ранних этапах миграции; отдельный SLA-мониторинг задержки; алертинг при превышении допустимого порога |
| **Потеря сообщений в Kafka (платежи, рисковые события)** | Неполная история транзакций, разрыв трассировки, сбои в примирении, финансовые расхождения | Низкая | Конфигурация replication.factor=3 и min.insync.replicas=2; размещение брокеров в разных зонах доступности (AZ); мониторинг ISR и лага потребителей; фолбэк на файловые выгрузки с шифрованием; резервное копирование данных Kafka |
| **Незавершённый матчинг клиентов к моменту cutover** | Часть клиентов временно недоступна для полного обслуживания; ограничение продуктовых предложений | Средняя | Установление порога готовности (<= 2% спорных случаев); возможность частичного cutover с последующей обработкой хвоста в параллельном режиме; выделение ресурса для ручной обработки нерешённых дублей |
| **Сбой CDC-коннекторов (Debezium) из Core Banking** | Остановка потоков данных, рассинхронизация витрин DWH, задержки обновления UI | Средняя | Резервные механизмы выгрузки (ночные дампы); мониторинг состояния коннекторов с алертингом; обеспечение RTO <= 4 часа; дублирующие ETL-потоки на переходный период |
| **Нарушение SLA обновления витрин DWH** | Отображение устаревших данных в UI и BI-отчётах, принятие решений на основе неактуальной информации | Средняя | Переход на микропакетную загрузку с более частыми интервалами; кэширование в BI-слое; отображение метки времени последнего обновления в UI; реализация circuit breaker при превышении таймаутов |
| **Конфликты справочников статусов и состояний между системами** | Блокировка клиентских операций, некорректные переходы в state machine, ошибки в API и интерфейсах | Средняя | Создание единого справочника dim_status в DWH; запрет хардкода статусов в прикладном коде; обязательная маршрутизация всех запросов статуса через единый источник |
| **Утечка персональных и чувствительных данных в процессе миграции** | Регуляторные штрафы, репутационные потери, нарушение требований ИБ | Низкая-Средняя | Маскирование PII на уровне источника; шифрование всех передаваемых файлов и потоков (mTLS); разграничение доступа (RBAC) с аудитом; запрет прямых запросов к PII вне MDM-системы |
| **Сопротивление или нехватка ресурсов у команд RetailBank при декомиссии** | Срыв сроков вывода систем из эксплуатации, продление параллельного существования ландшафтов, рост бюджета | Средняя | Раннее вовлечение владельцев RB-систем (data discovery на этапе 1); фиксация сроков декомиссии в дорожной карте; регулярные статус-встречи; закрепление ответственности за каждую систему |
| **Ошибки на этапе cutover без своевременного обнаружения** | Распространение неконсистентных данных в consuming-системы, сложный и длительный откат | Низкая | Многоуровневая сверка (количественная + бизнес-проверки для VIP-сегмента); период усиленного мониторинга (минимум 2 недели после cutover); заранее протестированный фолбэк-сценарий с RTO 30-45 минут |
| **Неполнота lineage и метаданных в системе управления данными** | Затруднённое расследование инцидентов, отсутствие понимания происхождения данных, сложность аудита | Средняя | Автоматическая генерация lineage через dbt-документацию; обязательное тегирование data-продуктов; назначение владельцев для каждого объекта в DataHub; контроль SLA в системе метаданных |
| **Проблемы интеграции UI-слоя с новыми витринами DWH** | Невозможность отображения данных в интерфейсе, ошибки загрузки, деградация UX | Низкая-Средняя | Тестирование на стендах с реальными данными; поэтапное переключение (канареечный релиз); graceful degradation - показ данные временно недоступны при сбоях витрин |
| **Необходимость отката cutover** | Потеря 1-4 недель от графика, снижение доверия стейкхолдеров, дополнительные затраты | Средняя | Проведение комплексного пилота на 10% данных с целевым показателем 100% успеха; стресс-тестирование на полной нагрузке (1M+ клиентов); пробный cutover с обязательным откатом в staging-среде; получение GO/NO-GO от executive-комитета перед финальным переключением |

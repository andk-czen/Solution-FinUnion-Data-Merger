# Аналитическая модель

## Выбранная модель: «звезда»

| Тип таблицы | Пример | Назначение |
| --- | --- | --- |
| Fact | fact_transactions | Основные события: транзакции, суммы, статусы, остатки после операции |
| Dimension | dim_customer | «Золотая запись» клиента: global_client_id, ФИО, дата рождения, паспорт, владелец, доска (board) |
| Dimension | dim_account | Счёт: global_account_id, валюта, тип счёта, банк (FU/RB), дата открытия/закрытия |
| Dimension | dim_product | Продукт/тип карты/кредита: тип продукта, категория, линейка, владелец продукта |
| Dimension | dim_card | Карта (nullable — не у всех транзакций есть карта) |
| Dimension | dim_date | Календарь: дата, день/неделя/месяц/квартал/год, тип дня (рабочий/выходной), праздники |
| Dimension | dim_channel | Канал операции: мобильное приложение, интернет‑банк, ATM, POS, отделение, API |
| Dimension | dim_status | Справочник статусов: код статуса, описание, группа (активен/заблокирован/закрыт), владелец, допустимые переходы. |

## Почему «звезда» подходит для OLAP‑нагрузки

Вот переформулированный вариант с сохранением технического смысла:

- Оптимизация производительности BI-запросов. Модель «звезда» обеспечивает прямое соединение фактических таблиц с измерениями через единичный JOIN. Это критически важно для интерактивных дашбордов и фронтенд-слоёв (например, Vue + Naive UI), требующих мгновенных агрегаций, особенно при обработке больших массивов.
- Минимальная сложность сопровождения. Звёздочная структура отличается высокой наглядностью: отсутствуют многоуровневые вложенности, а логика связей между сущностями интуитивно понятна, что существенно упрощает документирование и дальнейшую поддержку модели.
- Высокая эффективность фильтрации и группировки. Операции среза по ключевым атрибутам (клиент, временные промежутки, каналы взаимодействия, статусы) выполняются максимально быстро. Это полностью покрывает базовые отчётные потребности: остатки на счетах, активность по каналам, мониторинг просроченной задолженности.
- Естественная интеграция с оркестраторами и dbt. Архитектурный паттерн dbt (staging → dim → fact) идеально ложится на звёздочную модель. Написание валидационных проверок (на уникальность, пропуски, допустимые диапазоны значений) становится прозрачным и предсказуемым.
- Гибкая поддержка историчности данных. Реализация SCD Type 2 (с полями валидности valid_from/valid_to) позволяет вести полный аудит изменений клиентских профилей, таких как обновление паспортных данных или смена законного представителя.
- Прозрачное управление доступом и валидацией. В технической документации однозначно фиксируется использование суррогатных ключей для всех JOIN-операций, отсутствие строгих внешних ключей на уровне DWH и делегирование контроля целостности инструментам оркестрации и тестам dbt.
- Сквозная прослеживаемость и аудит. Наличие идентификатора kafka_event_id в фактических таблицах обеспечивает мгновенную трассировку от строки отчёта до исходного события в Kafka или Lakehouse. Это значительно ускоряет расследование расхождений и анализ происхождения конкретных сумм или статусов.

# Сравнение архитектурных вариантов

## 1. DWH на PostgreSQL

**Плюсы**
- Оперативное развёртывание: команда ИТ уже владеет SQL Server и реляционными СУБД (опыт специалистов уровня Vadim), что обеспечивает минимальный порог входа.
- Жёсткая схемная модель и полная поддержка ACID — оптимально для нормативной отчётности, где критична воспроизводимость метрик.
- Зрелая экосистема BI-инструментов, простота эксплуатации и встроенные механизмы бэкапирования.
- Экономически эффективна при работе с данными среднего объёма.

**Минусы**
- Слабая горизонтальная масштабируемость при обработке крупных массивов исторических/событийных данных (многолетние транзакционные архивы двух кредитных организаций).
- Отсутствие встроенных механизмов обработки полуструктурированных данных и потоковой аналитики в промышленном масштабе.
- Негибкая схемная модель затрудняет интеграцию новых источников (например, clickstream цифровых каналов) без выполнения миграций.
- Высокая стоимость содержания архивных данных в реляционной БД (стоимость владения превышает хранение в объектных хранилищах).

**Когда подходит.** Средний объём данных, приоритет — нормативная отчётность со стабильной схемой; сырая событийная аналитика не в фокусе.

**Применимость к кейсу.** Эффективное **промежуточное** решение на 3 месяца (переходная стадия): позволяет оперативно обеспечить консолидированную отчётность по клиентам, счетам, продуктам и операциям, минуя длительное внедрение Lakehouse. Не является подходящим единым целевым хранилищем на 12 месяцев — не справится с архивами двух банков и требованиями риск-моделирования на уровне сырых событийных данных.

## 2. Data Lakehouse

**Плюсы**
- Консолидированная платформа для сырых, архивных и событийных данных с использованием открытых форматов таблиц Iceberg - устраняет необходимость дублирования инфраструктуры Lake и Warehouse.
- Горизонтальная масштабируемость и низкая стоимость хранения на базе объектных хранилищ.
- Поддержка ACID-транзакций и эволюции схем поверх Iceberg - решает ключевую историческую проблему Data Lake data swamp.
- Единый слой данных для всех потребителей: BI через Trino, риск-модели и ML через Spark.


**Минусы**
- Повышенная сложность эксплуатации и оркестрации по сравнению с классическим DWH.
- Необходимость зрелой инженерной культуры: управление партиционированием, compaction, каталогизация таблиц.
- Нормативная отчётность с жёсткими SLA и построчной аудируемостью реализуется труднее, чем в классическом DWH с устоявшейся звёздной моделью.

**Когда подходит.** Большие объёмы и разнообразие данных: структурированные, событийные и полуструктурированные; широкая аудитория потребителей - не только BI, но и риск-модели, антифрод, ML.

**Применимость к кейсу.** Прямое покрытие двух ключевых проблем кейса: Data Lake есть только частично у FinUnion и полностью отсутствует у RetailBank. Оптимальный выбор для архивных данных карточных операций, клиентских событий цифровых каналов и общего целевого хранения крупных массивов данных на горизонте 12 месяцев.

## 3. Data Mesh

**Плюсы**
- Устранение узкого места центральной команды данных: домены Party, Account and Lending, Payments, Card и Servicing самостоятельно владеют своими data-продуктами и отвечают за их качество.
- Естественное соответствие организационной структуре банка после слияния: у FinUnion и RetailBank уже сформированы различные бизнес-направления с уникальной экспертизой в собственных данных.
- Ускорение разработки новых аналитических кейсов, поскольку данные не проходят через единый DWH-конвейер.


**Минусы**
- Критическая зависимость от зрелой платформенной инфраструктуры: self-service, стандарты интероперабельности - банк, недавно переживший слияние с разрозненными данными, ещё не готов к полностью децентрализованной модели.
- Риск воспроизведения проблемы кейса на новом уровне: при отсутствии сильного governance домены вновь могут разойтись в форматах и терминологии - та же рассинхронизация FU/RB, которая привела к текущей ситуации.
- Усложнение обеспечения единой регуляторной отчётности, если каждый домен ведёт данные по собственным правилам.


**Когда подходит.** Организации с высокой зрелостью данных, множеством независимых доменных команд и устоявшимися платформенными стандартами.

**Применимость к кейсу.** Полноценный Data Mesh преждевременен для FinUnion и RetailBank на горизонте 12 месяцев - сначала необходима консолидация через MDM и единый DWH или Lakehouse, иначе домены унаследуют текущий разнобой. Однако элементы Data Mesh - доменные data-продукты поверх общей платформы - применимы уже сейчас, что раскрыто в файле data-products.md.

## Итоговый выбор: гибридная архитектура

**Выбран гибридный подход: DWH на базе PostgreSQL на первом этапе плюс Data Lakehouse, с элементами Data Mesh поверх общей платформы.**

**Обоснование:**
- **3 месяца** - DWH на PostgreSQL закрывает срочную потребность в единой нормативной отчётности без длительного внедрения Lakehouse-инфраструктуры (см. dwh-lakehouse.md для деталей).
- **12 месяцев** - Data Lakehouse через Iceberg и Trino становится основным хранилищем для больших исторических и событийных данных; DWH сохраняется для нормативной отчётности с жёсткими SLA и аудируемостью (может быть реализован поверх той же платформы через Trino-представления или мигрировать на MPP-решение при росте нагрузки - вне рамок данного задания).
- **Data Mesh как организационная надстройка**, а не как замена технологической платформе: доменные команды Party, Account and Lending, Payments, Card и Servicing владеют своими data-продуктами, публикуемыми поверх единого DWH или Lakehouse и каталогизируемыми в DataHub - то есть используется governance-модель Data Mesh без полной децентрализации инфраструктуры, что снижает риск повторного расхождения данных после слияния.


Чистый DWH на PostgreSQL как единственное целевое решение отклонён из-за ограниченной масштабируемости для истории двух банков. Чистый Data Mesh отклонён как преждевременный для организации, ещё не завершившей базовую консолидацию данных.

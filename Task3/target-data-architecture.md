# Целевая архитектура данных (12 месяцев)

## Компоненты и их роль

### Operational Systems
Объединённые операционные системы по завершении перехода RetailBank: объединённая Core Banking система (управление счетами, договорами, транзакциями), централизованная карточная инфраструктура, единая Lending-платформа, Payment Hub, система управления обращениями (Case). Данные системы выступают источником истины для операционных сущностей — Счёт, Карта, Кредит, Договор, Транзакция, Платёж, Обращение (MDM для них мастером не является).

### MDM (Customer Hub + Reference Data)
Фундаментальный источник золотых записей для сущностей Клиент, Продукт, Тариф, Отделение и Контрагент. К сроку 12 месяцев MDM представляет собой не вспомогательный слой, а полноценную систему записи для указанных объектов: операционные платформы осуществляют чтение данных из MDM вместо ведения собственных копий справочников.

### Integration Layer
Реализует два направления взаимодействия:
- **Синхронный** (API Gateway / ESB) - для операций, требующих мгновенного ответа: верификация клиента при открытии продукта, запрос текущего баланса, обращение к MDM за golden client_id при клиентском обслуживании.
- **Асинхронный / CDC**  - для трансляции изменений без перегрузки операционных систем через публикацию событий в Kafka.

### Kafka (событийная шина)
Инфраструктура для всех потоков событий: транзакционные обновления (CDC-топики), бизнес-события (создание новой транзакции, инициирование платежа, регистрация обращения). Потребители: Data Lakehouse (потоковая фиксация), Graph DB (антифрод-мониторинг в реальном времени), поисковый движок (индексирование обращений).

### DWH
Инфраструктура нормативной отчётности: управленческая и регуляторная. Содержит историзированные агрегаты и факт-таблицы для BI и подготовки выгрузок для надзорных органов. Формирование данных через Airflow-пайплайны (batch/dbt) из операционных платформ и из Lakehouse (консолидация сырых событий).

### Data Lakehouse (Iceberg + Trino)
Хранилище больших исторических массивов и событийных данных: полная регистрация транзакций, архив карточных операций, клиентские события цифровых каналов, базовые данные для риск-моделей.

### BI
Аналитические панели и бизнес-аналитика: обращается к DWH за нормативными витринами и к Lakehouse (через Trino) - для ad-hoc исследований на уровне сырых и исторических данных.

### Airflow
Оркестрация всех batch-пайплайнов: транспортировка данных в DWH, консолидация Lakehouse → DWH, архивирование в объектное хранилище, публикация lineage в DataHub.

### DataHub (каталог данных)
Платформа каталогизации, прослеживаемости и управления владельцами данных. Агрегирует метаданные от MDM, DWH, Lakehouse и Airflow - обеспечивает требуемую трассируемость происхождения данных согласно ограничениям проекта.

## Принципы, заложенные в архитектуру

- **Разделение OLTP/OLAP.** Операционные системы никогда не опрашиваются напрямую BI или регулятором - взаимодействие осуществляется исключительно через DWH или Lakehouse, что напрямую удовлетворяет ограничению на отсутствие аналитической нагрузки на операционные системы.
- **MDM как единственный источник golden record** для клиентских и справочных сущностей - ликвидация проблемы дублирования и рассинхронизации, выявленной в кейсе.
- **CDC как основной механизм синхронизации** к сроку 12 месяцев вместо batch-выгрузок промежуточного периода на 3 месяца - обеспечивает снижение задержки между операционными системами и аналитическими потребителями.
- **Единая точка каталогизации (DataHub)** для всех хранилищ обеспечивает прослеживаемость и совместима с доменной моделью владения (Task 2) и BIAN-доменами (Task 1).
- **Регулятор и клиентские каналы — внешние акторы**, не имеющие прямого доступа к внутренним хранилищам: регулятор получает только нормативные выгрузки из DWH, каналы (мобильное/веб) взаимодействуют исключительно с операционными системами.

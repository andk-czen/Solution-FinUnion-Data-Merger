# Cравнение

## Cравнение DWH на PostgreSQL и Data Lakehouse для кейса FinUnion + RetailBank

| Критерий | DWH на PostgreSQL | Data Lakehouse |
|---|---|---|
| Объём данных | Эффективен для агрегатов и нормативных витрин; неоптимален для полных архивов транзакций двух кредитных организаций | Спроектирован для масштабных массивов; экономичное хранение на базе объектных хранилищ |
| Скорость внедрения | Оперативный запуск — минимум дополнительной инфраструктуры, использование известного SQL-стека | Более продолжительный цикл — необходима настройка Iceberg-каталога, Spark/Trino, конфигурирование партиционирования |
| Регламентированная отчётность | Ключевое преимущество: строгая схемная модель, ACID, воспроизводимость метрик для надзорных органов | Осуществима через Trino, однако исторически подобные гарантии требуют повышенной дисциплины (compaction, snapshot-изоляция) |
| Событийные/сырые данные (клик-стрим, полная история карт) | Неэффективен как первичное хранилище | Прямое предназначение — открытый формат, schema evolution, обработка полуструктурированных массивов |
| Риск-модели / ML на исторических данных | Ограниченно применим, экономически нецелесообразен при масштабных выборках | Эффективен — Spark/Trino поверх единых Iceberg-таблиц без необходимости выделения дополнительного слоя |
| Стоимость хранения истории | Повышенная (реляционная инфраструктура) | Сниженная (объектное хранилище + открытый формат) |
| Готовность закрыть проблему 'нет Data Lake у RetailBank' | Не устраняет | Непосредственно устраняет |


## Выбранный подход для промежуточного состояния (3 месяца)

На 3 месяца выбран **DWH на PostgreSQL** как единственное аналитическое хранилище.

Аргументация:
- Оперативный результат: минимально жизнеспособный ландшафт для совместной отчётности по клиентам, счетам, продуктам и операциям - именно тот результат, который требуется на переходном этапе кейса.
- Масштаб данных, необходимых для управленческой отчётности на данном горизонте (агрегаты, а не полные сырые архивы), полностью укладывается в производительные возможности PostgreSQL.
- Развёртывание Lakehouse-инфраструктуры (Iceberg-каталог, Spark/Trino, потоковые конвейеры) в течение 3 месяцев параллельно с MDM и матчингом клиентов создаст избыточную нагрузку на проект; приоритет - сначала стабилизация клиентских данных.
- Простой batch-конвейер для данного состояния описан в data-pipelines.md (конвейер номер 2).


## Выбранный подход для целевого состояния (12 месяцев)

К 12 месяцам основным хранилищем для больших исторических и событийных данных становится **Data Lakehouse на базе Apache Iceberg**, а **DWH сохраняется**, но его роль сужается до регламентированной отчётности:
- **DWH (PostgreSQL или её целевая эволюция)** - управленческая и нормативная отчётность: агрегированные, историзированные (SCD2) витрины с воспроизводимыми цифрами для регулятора и финансового департамента. Здесь важна не гибкость схемы, а стабильность и аудируемость.
- **Data Lakehouse** - полный поток транзакций и событий, история карточных операций до слияния, клиентские события каналов, сырьё для риск-моделей и антифрода. Здесь важен объём, гибкость схемы и доступ для ML и аналитиков без выгрузки в отдельные системы.


## Роль Apache Iceberg и Trino

- **Apache Iceberg** - формат таблиц поверх объектного хранилища, обеспечивающий Lakehouse функциональность, недоступную классическому Data Lake: транзакционная целостность ACID, snapshot-изоляция (критично для сверки сумм и аудита), schema evolution (возможность добавления полей без перезаписи всей таблицы, что существенно при поэтапной миграции RetailBank), партиционирование и compaction для поддержания производительности при масштабировании. Iceberg-таблицы применяются для архивов транзакций, карточных операций и событий клиентских каналов.
- **Trino** - распределённый SQL-движок, выполняющий две функции: (1) предоставляет BI-системам и аналитикам единый SQL-интерфейс к Iceberg-таблицам без необходимости использования Spark; (2) обрабатывает федеративные запросы, консолидирующие DWH и Lakehouse в одном SQL-запросе, что позволяет BI обращаться к логическому слою поверх обоих хранилищ без предварительного определения физического расположения данных.


## Какие данные остаются в DWH, какие попадают в Lakehouse и почему

| Данные | Хранилище | Почему |
|---|---|---|
| Регламентированные витрины по Клиенту, Счёту, Продукту, Кредиту (агрегаты) | DWH | Требуется строгая схемная модель, воспроизводимость показателей, соответствие нормативным формам |
| Полная история транзакций (включая период до слияния, по обеим организациям) | Lakehouse | Крупный объём, необходим доступ риск-моделей и антифрода на детализированном уровне |
| История карточных операций FU + RB | Lakehouse | Значительный объём, полуструктурированные архивные выгрузки от RetailBank |
| Клиентские события каналов (мобильное/веб) | Lakehouse | Высокая частота генерации, полуструктурированный формат, не задействуются в нормативной отчётности |
| Нормативная отчётность (выходной агрегат) | DWH | Формируется из регламентированных витрин DWH, а не напрямую из Lakehouse |
| Данные для ad-hoc аналитики и ML на истории | Lakehouse (через Trino/Spark) | Гибкая схема, нет необходимости заблаговременного моделирования всех возможных запросов |


## Ограничения выбранного подхода

- Наличие двух хранилищ вместо одного повышает операционную сложность: требуется поддерживать согласованность между агрегатами в DWH и детальными данными в Lakehouse (риск расхождения при сбое конвейера агрегации).
- Trino как единая точка доступа превращается в критический компонент — его простой затрагивает и BI, и федеративные запросы; необходима выделенная политика SLA и мониторинг.
- Iceberg требует инженерной дисциплины: без регулярного compaction и управления партициями производительность снижается при росте объёма данных от двух организаций.
- Миграция PostgreSQL DWH на целевую платформу (при увеличении нагрузки нормативной отчётности) не входит в 12-месячный горизонт данного проекта и потребует отдельного анализа (например, переход на MPP-СУБД или колоночное хранилище), если объём нормативной отчётности увеличится.
- Гибридный подход обходится дороже, чем единое решение (исключительно DWH или исключительно Lakehouse), из-за большего количества поддерживаемых компонентов; эта инвестиция оправдана тем, что закрывает различные, не взаимозаменяемые классы задач кейса (нормативная отчётность versus масштабные событийные данные).
